# idle-reaper 설계

> 상태: 초안 (v1alpha1 설계 중)
> 이 문서가 먼저고 코드가 나중이다. 결정이 바뀌면 여기부터 고친다.

## 1. 문제

개발 환경은 근무 시간 외에 사실상 놀지만 노드 비용은 그대로 나간다.
주 168시간 중 근무는 55시간, **나머지 113시간(67%)이 유휴**다.

흔한 해법은 클러스터 **바깥**의 스케줄러(cron·EventBridge+Lambda 등)가
정해진 시각에 워크로드를 축소하는 것이다. 동작은 하지만 구조적 한계가 있다.

| 한계 | 왜 문제인가 |
|---|---|
| 클러스터 내부 상태를 모름 | 사람이 수동으로 올려둔 것, HPA가 조정 중인 것을 구분 못 함 |
| 설정이 개발자에게 안 보임 | 스케줄이 외부 코드·환경변수에 있어 `kubectl`로 확인 불가 |
| 한 번 쏘고 끝 | 이벤트를 놓치면 그날은 그냥 안 됨. 드리프트 교정이 없음 |
| 권한 모델이 분리됨 | 클러스터 RBAC과 별개로 IAM을 따로 설계해야 함 |

이 한계들은 전부 **"바깥에서 이벤트로 조작한다"**는 구조에서 나온다.
클러스터 안에서 **상태를 지속 조정**하는 방식으로 바꾸면 사라진다.

## 2. 목표 / 비목표

### 목표

- 네임스페이스 단위로 **유휴 시간대를 선언**한다 (명령이 아니라 선언)
- 선언한 시간대에 대상 워크로드를 축소하고, 벗어나면 **원래 규모로 복구**한다
- 컨트롤러 재시작·이벤트 유실·수동 변경 이후에도 **선언한 상태로 수렴**한다
- **회수한 리소스량을 보고**한다 (비용 효과의 근거)

### 비목표 (명시적으로 안 한다)

| 안 하는 것 | 이유 |
|---|---|
| 노드 직접 관리 (cordon/drain/삭제) | 노드 회수는 Karpenter 등 노드 오토스케일러 책임. 같은 대상을 두 컨트롤러가 다투면 위험 |
| StatefulSet 지원 | 데이터가 붙어 있어 축소 위험도가 다르다. v1alpha1 범위 밖 |
| 비용 **금액** 산출 | 단가·약정 정보가 클러스터 안에 없다. 금액은 이 문서의 모델로만 다룬다 |
| prd 보호 로직 | 네임스페이스 이름으로 판단하는 건 취약하다. RBAC과 배포 정책으로 막는 게 맞다 |

## 3. 참조 환경과 절감 모델

> **이 장은 랩 클러스터와 아무 관계가 없다.**
> 랩에서는 금액을 잴 수 없다 — 노드 오토스케일러도 없고 단가 정보도 없다.
> 그래서 랩에서 **실측한 회수량**을 대입할 **가상의 운영 환경**을 문서상으로 정의한다.

| | 랩 클러스터 | 참조 환경 |
|---|---|---|
| 노드 | control-plane 1 + worker 3 | 6대 |
| 실체 | 로컬 도커 컨테이너 | **없다. 계산용 가정** |
| 비용 | 0 | 월 약 $1,019 |
| 여기서 얻는 것 | 회수한 request 량 (**실측**) | 금액 환산 (**모델**) |

둘을 섞어서 "랩에서 45% 절감했다"고 말하는 것은 거짓이다.
정확한 표현은 **"랩에서 측정한 회수량을 참조 환경에 대입하면 45%에 해당한다"** 이다.

### 환경 가정

| 항목 | 값 |
|---|---|
| 워크로드 | 마이크로서비스 20개 × replica 2 = 파드 40개 |
| 파드 평균 request | CPU 500m / Mem 1Gi |
| 총 request | 20 vCPU / 40 GiB |
| 노드 | `m5.xlarge` (4 vCPU / 16 GiB) |
| 단가 | 온디맨드 약 $0.236/h *(검증 필요)* |

노드 수는 CPU가 제약한다.

```
20 vCPU ÷ 3.9 (allocatable, 시스템 예약 제외) ≈ 5.1  →  여유 포함 6대
40 GiB  ÷ 14.5                               ≈ 2.8  →  메모리는 제약이 아님
```

기준 비용: `6 × $0.236 × 720h ≈ $1,019/월`

### 회수 모델

**노드는 0이 되지 않는다.** CoreDNS 2 replica와 Ingress 컨트롤러가
anti-affinity로 분산되므로 유휴 시간에도 **최소 2대**가 남는다고 가정한다.

| 구간 | 노드 | 주당 시간 |
|---|---|---|
| 근무 (평일 09–20시) | 6대 | 55h |
| 유휴 | 2대 | 113h |

```
절감 = 4대 × $0.236/h × 113h × 4.33주 ≈ $462/월
$1,019 → $557  (약 45%)
```

시간의 67%를 회수하는데 비용은 45%만 줄어드는 이유는 **베이스라인 2대를 없앨 수 없어서**다.

### 베이스라인 민감도

이 모델에서 가장 민감한 값은 **유휴 시간에 남기는 노드 수**다.

| 유휴 베이스라인 | 회수 노드 | 월 절감 | 절감률 |
|---|---|---|---|
| 1대 | 5대 | ~$577 | 56% |
| **2대 (채택)** | **4대** | **~$462** | **45%** |
| 3대 | 3대 | ~$346 | 34% |

2대를 택한 이유:

- 1대는 CoreDNS·Ingress의 HA를 포기하는 구성이라 운영 환경 가정으로 부적절하다
- 베이스라인을 낮게 잡을수록 절감률이 커지는데, **근거 없이 큰 숫자는 과장으로 읽힌다.**
  보수적으로 잡고 민감도를 함께 밝히는 편이 낫다

### 모델에 붙는 단서

- **Spot을 쓰면** 단가는 내려가지만 절감 **비율**은 그대로다
- **RI/Savings Plans 약정분은 꺼도 과금된다.** 유휴 회수의 실제 대상은
  온디맨드·Spot 구간뿐이다. 약정 비중이 높은 환경에서는 절감폭이 모델보다 작다

## 4. API 초안

```yaml
apiVersion: finops.b100to.dev/v1alpha1
kind: IdleWindow
metadata:
  name: dev-nights
  namespace: team-a
spec:
  selector:
    matchLabels: { app.kubernetes.io/part-of: backend }
  sleepAt: "0 20 * * 1-5"
  wakeAt:  "0 9 * * 1-5"
  timezone: Asia/Seoul
  minReplicas: 0
  skipIfHPA: true
  respectManualScale: true
status:
  phase: Asleep
  reclaimed:
    cpu: "16000m"
    memory: "32Gi"
  affectedWorkloads: 20
  conditions: [...]
```

네임스페이스 스코프다. 개발자가 **자기 네임스페이스에 직접 선언**하는 것을 전제한다.

## 5. 설계 결정

### D1. 원래 replica를 어디에 저장하는가

**선택: 대상 Deployment의 annotation.**

- 버린 대안: `IdleWindow.status`
- 근거: IdleWindow를 지우거나 컨트롤러가 사라져도 **복구 정보가 워크로드에 남아야 한다.**
  status에 두면 "재우는 주체가 사라졌는데 워크로드는 0으로 남는" 최악의 상태가 가능하다
- 대가: 남의 오브젝트를 건드린다. annotation 키에 소유자를 명시해 충돌을 줄인다
- 리스크: 사람이 annotation을 지우면 복구 불가 → 그때는 `minReplicas`가 아니라 **1로 안전 복구**

### D2. 스케줄 도래를 어떻게 감지하는가

**선택: `RequeueAfter`로 다음 경계 시각까지 재큐.**

- 버린 대안: 별도 cron 고루틴
- 근거: 컨트롤러가 재시작해도 다음 reconcile에서 현재 시각을 다시 계산하면 복구된다.
  타이머를 따로 들고 있으면 그 상태가 프로세스에 묶여 유실된다
- 정확도 가정: **분 단위면 충분하다.** 야간 축소에 초 단위 정확도는 불필요

### D3. 수동 변경을 어떻게 판정하는가

**선택: 마지막으로 컨트롤러가 적용한 값을 annotation에 함께 남기고, 현재 값과 비교.**

현재 replica가 컨트롤러가 적용한 값과 다르면 = 사람이 건드린 것 → **다음 경계 시각까지 존중**한다.

- 근거: 사람이 급해서 올린 것을 자동화가 되돌리면 사고다
- 리스크: 다른 컨트롤러(GitOps 동기화 등)가 바꾼 것도 "사람"으로 판정된다.
  이건 v1alpha1의 알려진 한계로 둔다

### D4. HPA가 붙은 워크로드

**선택: `hpaPolicy` 로 정책을 고르게 한다. 기본값은 `Warn`.**

| 값 | 동작 |
|---|---|
| `Skip` | 조용히 건너뛴다 |
| **`Warn`** (기본) | 건너뛰되 Event 와 condition 으로 밝힌다 |
| `Scale` | 다른 워크로드와 동일하게 취급한다 |

- 버린 대안: `skipIfHPA` 불리언 하나로 켜고 끄기
- 근거: 처음엔 "건너뛴다/안 건너뛴다"의 문제로 봤는데, 실제로는 **무엇을 할지**와
  **얼마나 알릴지**가 다른 축이었다. 그리고 침묵이 틀린 답이다 — 줄지 않은 워크로드야말로
  이 오브젝트를 보는 사람이 알아야 하는 것이고, dev 에 붙은 HPA 는 대개 실수라
  흡수할 게 아니라 드러낼 대상이다
- `Scale` 을 기본으로 두지 않는 이유: 같은 필드를 두 컨트롤러가 쓰면 진동한다.
  HPA 가 잠들어 있다고 아는 사람만 선택해야 한다

### D4-1. PDB 는 정책이 아니라 관측 대상

PDB 는 replica 를 바꾸는 것을 막지 않는다. **evict 를 막는다.** 그래서 이 컨트롤러가
축소하는 데는 지장이 없지만, 노드를 비우는 데는 지장이 있다 — 그리고 비용은
노드 쪽에서 나온다.

- `status.blockingPDBs` 로 보고만 한다. 정책 필드를 두지 않는다
- 판정은 spec 이 아니라 `status.disruptionsAllowed` 를 읽는다. eviction API 가
  실제로 강제하는 숫자가 그것이다
- **`currentHealthy > 0` 조건을 함께 본다.** 워크로드가 이미 0 이면 같은
  `disruptionsAllowed: 0` 이 "거부"가 아니라 "막을 게 없음"을 뜻한다.
  이 조건이 없으면 회수에 성공한 순간에 정확히 경보가 뜬다

### D5. 노드에 관여하지 않는다

파드를 0으로 만들어도 **노드가 사라져야 비용이 준다.** 그 일은 노드 오토스케일러가 한다.

이 컨트롤러는 앞단(파드 축소)만 맡고, 노드는 건드리지 않는다.
파드를 비워도 노드가 안 죽는 흔한 원인은 다음과 같으며, 이는 이 컨트롤러가
해결할 문제가 아니다.

- 시스템 파드가 노드를 붙잡음
- 남은 파드가 PDB에 걸려 evict 불가
- `emptyDir` 등 로컬 스토리지 사용 파드
- 노드가 노드 오토스케일러 관리 대상이 아니거나, 노드그룹 최소 대수에 걸림

**다만 몇 대가 비워졌는지는 센다.** 파드를 0으로 만든 것만으로는 비용이 줄지
않는다. 노드가 사라져야 줄고, 노드는 evict 해야 할 파드가 남아 있지 않을 때만
사라진다. 그래서 `status.drainableNodes` 로 "지금 몇 대가 제거 가능한 상태인가"를
보고한다.

판정 기준은 노드 오토스케일러와 같다 — **DaemonSet 파드는 계산에서 제외한다.**
DaemonSet 파드는 다른 노드로 옮길 대상이 아니라 노드와 함께 사라지기 때문이다.
Karpenter 의 consolidation 과 Cluster Autoscaler 의 scale-down 판정이 같은 규칙을
쓴다. 이 컨트롤러는 DaemonSet 을 건드리지 않는다.

제거 자체는 여전히 노드를 관리하는 쪽의 일이다. 세는 것과 지우는 것을 나눠야
같은 자원을 두 컨트롤러가 다투지 않는다.

### D6. Deployment 변경을 감시한다

**선택: IdleWindow 뿐 아니라 Deployment 도 watch 하고, 바뀐 Deployment 를 선택하는
IdleWindow 들로 되돌려 큐에 넣는다.**

- 버린 대안: IdleWindow 만 watch 하고 `RequeueAfter` 주기에 맡긴다
- 근거: 처음에는 시간 기반 컨트롤러라 자기 타이머만 있으면 된다고 봤다. 그런데
  손으로 스케일한 워크로드를 **최대 10분간 인지하지 못했다**(D2 의 requeue 상한).
  드리프트 교정이 컨트롤러를 쓰는 이유인데, 10분 늦게 교정하는 것은 그 이유를
  절반만 만족한다. watch 를 붙이자 같은 상황이 4초 안에 반영됐다
- 대가: 네임스페이스의 모든 Deployment 변경마다 매핑 함수가 돈다. 매핑은
  같은 네임스페이스의 IdleWindow 만 조회하므로 비용은 작다

## 구현하며 바뀐 것

- **D6 이 새로 생겼다.** 설계 단계에서는 시간 기반이니 자기 타이머면 충분하다고
  보았는데, 수동 변경 테스트에서 반영이 10분까지 늦는 것을 보고 뒤집혔다
- **`spec.suspend` 추가.** 장애 중에 오브젝트를 지우지 않고 멈출 수단이 필요했다
- **`status.skippedWorkloads` 추가.** 건너뛴 것을 세지 않으면 `scaled: 0` 만 보여
  고장인지 의도인지 구분할 수 없다
- **cron 은 "지금이 두 시각 사이인가"를 답하지 못한다.** 과거를 뒤지는 대신 다음
  경계 두 개를 비교해 판정한다(D2). 상태를 저장하지 않아도 되는 형태라 재시작
  복구가 공짜로 따라온다
- **selector 를 필수에서 선택으로 뒤집었다.** 빈 selector 가 아무것도 선택하지
  않게 해 두었는데, 이 오퍼레이터가 하려는 말은 "이 네임스페이스는 이 시간대에
  유휴다"이고 그건 보통 전체에 대한 진술이다. 전체가 기본이고 selector 는
  덜어내는 수단인 편이 맞다
- **`status.drainableNodes` 를 추가했다.** 파드를 0 으로 만드는 것까지만 보고하면
  "그래서 얼마 아꼈나"에 답할 수 없다. 노드가 사라져야 비용이 줄고, 그 직전
  상태(제거 가능한 노드 수)는 이 컨트롤러가 셀 수 있다
- **selector 를 필수에서 선택으로 뒤집었다.** 빈 selector 가 아무것도 선택하지
  않게 해 두었는데, 이 오퍼레이터가 하려는 말은 "이 네임스페이스는 이 시간대에
  유휴다"이고 그건 보통 전체에 대한 진술이다
- **`status.drainableNodes` 를 추가했다.** 파드를 0 으로 만드는 것까지만 보고하면
  "그래서 몇 대가 비었나"에 답할 수 없다
- **`skipIfHPA` 불리언을 `hpaPolicy` 3값으로 바꿨다.** 무엇을 할지와 얼마나 알릴지가
  다른 축이라는 것을 나중에 알았다
- **PDB 오탐을 만들었다가 고쳤다.** `disruptionsAllowed == 0` 만 보면 워크로드가
  0 으로 내려간 순간 — 즉 성공한 순간 — 에 경보가 뜬다. `currentHealthy > 0` 을
  함께 봐야 한다
- **Fargate 노드를 워커에서 제외했다.** EKS 는 Fargate 파드마다 합성 노드를
  만드는데, 그 노드는 파드 때문에 존재하므로 영원히 drainable 이 되지 않는다.
  컨트롤러 자신을 Fargate 에 올리는 구성이 흔해서 실제로 마주칠 문제다
- **컨트롤러 자신도 노드가 필요하다.** 워커가 0 이 되면 깨워줄 주체가 사라진다.
  회수 대상이 아닌 노드나 Fargate 에 배치해야 한다. Karpenter 가 자기 자신에게
  같은 제약을 두는 것과 같은 이유다
- **런타임 이미지에 tzdata 가 없다.** `_ "time/tzdata"` 로 내장하지 않으면 개발
  머신에서만 동작하고 클러스터에서 `Asia/Seoul` 로드가 실패한다

### D7. 알림은 노출까지만 한다

**선택: condition · Event · 메트릭 세 가지로 노출하고, 라우팅은 하지 않는다.**

| 계층 | 답하는 질문 | 갱신 시점 |
|---|---|---|
| condition | 지금 막혀 있는가 | 매 reconcile |
| Event | 언제부터 막혔는가 | **변할 때만** |
| 메트릭 | 얼마나 오래 막혀 있었는가 | 매 reconcile |

- condition 과 Event 의 역할을 처음에 섞었다. 차단 요인을 매 reconcile 마다
  Event 로 쐈더니 33초에 13건이 쌓였다. **condition 은 상태고 Event 는 사건이다.**
  일주일 막혀 있으면 이벤트 수천 건에 새 정보는 0이 된다. 조건이 바뀔 때만 쏜다
- 메트릭이 따로 필요한 이유: Event 는 기본 한 시간이면 만료돼 "오후 내내 막혀
  있었나"에 답할 수 없고, condition 은 그 오브젝트를 읽는 쪽에만 보인다.
  시간에 걸쳐 평가할 수 있는 것은 게이지뿐이다
- 노드 수는 클러스터 속성이라 window 라벨을 붙이지 않는다. 붙이면 네임스페이스가
  둘일 때 같은 숫자가 두 번 나가고 `sum()` 에서 중복 계산된다
- IdleWindow 가 삭제되면 해당 라벨 조합을 지운다. GaugeVec 는 한 번 본 라벨을
  계속 들고 있어서, 지우지 않으면 없는 오브젝트가 마지막 값을 영원히 보고한다
- **Slack 같은 라우팅은 넣지 않는다.** 알림 정책을 오퍼레이터에 묻으면 웹훅 URL과
  토큰을 들고 있어야 하고, 다른 클러스터에 그대로 쓸 수 없게 된다

## 6. 실패 모드

| 상황 | 기대 동작 |
|---|---|
| 컨트롤러가 wake 시각 동안 죽어 있었음 | 재기동 후 첫 reconcile에서 현재 시각 기준으로 즉시 복구 |
| 이벤트를 놓침 | 주기적 resync로 수렴. 이벤트 내용에 의존하지 않는다 |
| annotation이 지워짐 | 원본을 알 수 없음 → replica 1로 안전 복구하고 Event 기록 |
| 대상 10개 중 3개 실패 | 부분 성공을 허용하고 status·Event에 기록. 전체 롤백하지 않는다 |
| 타임존·서머타임 | `time.LoadLocation` 기준. UTC 고정하지 않는다 |

## 7. 검증 계획

| 랩에서 실측 가능 | 랩에서 검증 불가 |
|---|---|
| 지정 시각에 축소되는가 | 실제 노드 감소 |
| 원래 replica로 복원되는가 | 비용 절감 금액 |
| reconcile 반복 시 결과가 같은가 (멱등성) | Karpenter 연동 |
| 컨트롤러 재시작 후 수렴하는가 | |
| 수동 변경을 존중하는가 | |
| 회수한 request 량 | |

kind에는 노드 오토스케일러가 없다. **금액은 3장의 모델을 통해서만 이야기한다.**

## 8. 알려진 한계

- HPA가 붙은 워크로드는 회수 대상이 아니다 (D4)
- Deployment만 지원한다
- 수동 변경 판정이 다른 컨트롤러의 변경과 구분되지 않는다 (D3)
- 노드가 실제로 줄어드는지는 이 컨트롤러가 보장하지 않는다 (D5)
